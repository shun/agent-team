# agent-team 育成ロードマップ(成長型ブートストラップ)

このリポジトリに AI エージェントチームを導入するためのロードマップ。

一括セットアップはしない。**最初の一人(Gen)を最小構成で生み、Gen と人間が対話しながらチームと土台を少しずつ育てる。** 新メンバーは必要になったときに一人ずつ迎える。すべての変更は「小さく試す → 振り返る → 人間が承認する → 定義に反映する」の成長ループを通す。

設計思想の正本は [tmp/memo.md](../tmp/memo.md)(将来 docs/ 配下に整理予定)。

## 成長ループ(すべての変更の基本サイクル)

エージェント定義・docs・ワークフローの変更は、大小問わずこのループを通す。

```
1. 気づき・提案(人間 or エージェント)
2. 小さく試す(実タスクで使ってみる)
3. 振り返り(何が良かったか / 何がダメだったか)
4. 人間が判断(採用 / 却下 / 保留)
5. 採用分だけ正本 docs に反映し、growth-log に記録
```

memo セクション23 は「自己成長機構」を MVP 外としているが、あれは自動化された成長基盤のこと。ここでの自己成長は**人間承認つきの定義改善ループ**であり、自動化はしない。この解釈の違いは意図的なもの。

- [x] `docs/agent/team.md` — Gen 一人分の役割・責任・禁止事項だけ書く(他メンバー欄は「未加入」)

**完了条件**: Gen に依頼すると、`docs/work/current-task.md` に目的・範囲・完了条件を整理して返してくれる。

## Stage 1: Gen と二人三脚で土台づくり

最初のテーマは「チームの土台づくり」そのもの。Gen と対話しながら、必要になったファイルから順に作る。**最初から全ファイルを置かない。**

- [ ] `docs/work/current-task.md` の運用開始(テーマ: チーム土台の整備)
- [ ] `docs/agent/workflow.md` 初版 — この時点では「人間 ⇄ Gen」だけの最小フロー
- [ ] `docs/agent/safety.md` 初版 — 禁止事項(memo セクション20)。**これだけは最初から固定**(merge / deploy / 破壊操作 / 人間承認なしの決定の禁止など)
- [ ] `.ai/board/growth-log.md` — 成長ループの記録開始(日時 / 提案 / 試した結果 / 人間の判断)
- [ ] Gen 自身の定義を1回以上、成長ループで改善する(自己成長の練習台は Gen 自身)
- [ ] Gen が「次に必要な仲間と、その理由」を提案 → 人間が承認

**完了条件**: 成長ループが1周以上回り、growth-log に記録が残っている。

## Stage 2: 二人目 — Rin(リスク番人)を迎える

ここで確立する「メンバーの迎え方」の標準手順は、以降の全員に適用する。

- [ ] Gen が Rin の役割定義ドラフトを作る(`docs/agent/team.md` に追記: 役割・責任・成果物・判断基準・禁止事項)
- [ ] 人間がドラフトを承認
- [ ] `.claude/agents/rin.md` を作成(薄いアダプタ。詳細は docs/agent/team.md を参照させる)
- [ ] **試運転**: これまでに作った土台(AGENTS.md / workflow / Gen の定義)を Rin にレビューさせ、`docs/work/risk-review.md` に反対意見・弱点を出させる
- [ ] Rin の指摘を成長ループに載せて土台を修正
- [ ] 振り返り → Rin 自身の定義を修正 → growth-log に記録

**完了条件**: Rin が一般論ではない具体的な反対意見を出せている(出せていなければ定義を直すか、迎える順序を再検討)。

## Stage 3: 三人目 — Shino(要件整理)

- 迎える契機: 実テーマを扱い始めて、要件整理が Gen の手に余ると感じたとき
- [ ] 標準手順で迎える(Gen ドラフト → 人間承認 → アダプタ作成 → 試運転 → 振り返り)
- [ ] 試運転テーマ: 小さな実テーマ1つの `requirements.md` / `open-questions.md` 作成
- [ ] このあたりで `docs/work/` の成果物テンプレートを必要分だけ整備

## Stage 4: 四人目・五人目 — Kai(設計)、Toki(QA)

- 迎える契機: 設計判断が必要なテーマ(Kai)、確認観点の整理が必要なテーマ(Toki)が来たとき
- [ ] それぞれ標準手順で迎える(同時には迎えない。一人ずつ)
- [ ] Kai の試運転: 実テーマで `architecture-options.md`(複数案 + pros/cons 必須)
- [ ] Toki の試運転: 同テーマで `test-analysis.md`(人間がレビューできる粒度)
- [ ] 5人そろったら `docs/agent/workflow.md` を memo セクション16 の標準フローに更新

## Stage 5: フルサイクル検証

5人で1つのテーマを1周し、チームとして機能するかを検証する。

- [ ] 人間がテーマを提示(memo セクション29 の候補B/C 規模)
- [ ] 人間の依頼 → Gen → Shino → Kai → Toki → Rin → Gen 統合 → `final-proposal.md` → 人間判断
- [ ] memo の仮説1〜5を検証し、結果を記録
  - 名前付きで出力品質が上がったか / 成果物経由で反論・修正が成立したか / Rin が過剰合意を抑制したか / final-proposal だけで判断できたか / Markdown + 明示リンクで足りたか
- [ ] 失敗条件(memo セクション25)チェック — 特に「名前だけ増えて出力が同じ」「Rin が一般論だけ」「final-proposal が長すぎる」
- [ ] 生き残ったルールだけ `docs/decisions/ADR-0001-agent-team-policy.md` に固定(人間承認)

## 育成の原則

- **一度に迎えるのは一人まで。** 前のメンバーの試運転と振り返りが終わるまで次を迎えない
- **ファイルは必要になってから作る。** 最初から14ファイル置かない
- **人間の承認なしに正本(docs / エージェント定義)を変えない**
- **名前だけ増えて出力が変わらないメンバーは削る**(失敗条件)
- 迎える順序・役割分担は固定ではない。成長ループの中で人間と Gen が見直してよい
