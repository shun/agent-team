## 1. 重大リスク(P0)

### P0-1: 正本保護リストに AGENTS.md・CLAUDE.md・.claude/settings.json が含まれていない

- **対象**: safety.md 2節「正本 docs(docs/agent/ 配下・docs/roadmap.md・docs/decisions/・.claude/agents/ 配下)を人間の承認なしに変更しない」
- **指摘**: この限定列挙には、エージェントの挙動を最上流で決める **AGENTS.md** と **CLAUDE.md** が入っていない。将来置かれうる **.claude/settings.json(permissions / hooks)** も入っていない。文言どおりに読めば、エージェントが AGENTS.md から「作業前に safety.md を読むこと(MUST)」の行を削除しても、safety.md の禁止事項には違反しない。安全境界の入口を無承認で書き換えられる穴であり、境界文書自体は守られていても意味を失う。
- **失敗パターン**: 将来のセッションで「AGENTS.md は正本リストにないので整理してよい」と善意で解釈したエージェントが参照行を削り、以降のセッションが safety.md を読まずに動く。誰も違反していないのに境界が消える。
- **緩和策**: safety.md 2節の列挙に「AGENTS.md・CLAUDE.md・.claude/ 配下全体(agents/ に限定しない)」を追加する。一行の修正で塞がる。あわせて workflow.md 2節の権限表にも同じ行を足す。
- **判断**: **採用**(2026-07-05 人間)。緩和策どおり反映 → base-fix-draft.md 変更1・2

## 2. 重大リスク(P1)

### P1-1: 書き込み許可が「Gen」名義のままで、Rin の作業は明文上の許可がない

- **対象**: safety.md 4節「docs/work/ 配下の作業成果物は、**Gen** が人間の承認なしに作成・更新してよい(Q1 で確定)」、workflow.md 2節の表(列名が「**Gen 単独での**書き込み」)
- **指摘**: 禁止側の Q2 は「Gen を含むすべてのエージェント(今後迎えるメンバー・サブエージェントも同様)」(workflow.md 2節)と全員に一般化されたのに、許可側の Q1 は Gen 名義のまま残っている。いままさに Rin が書いているこの risk-review.md は、safety.md の文言上は許可されていない操作である。team.md Rin 節の成果物定義と safety.md が食い違っており、「矛盾したらより厳しい方を適用」(safety.md 冒頭)を素直に適用すると **Rin は何も書けない**。
- **失敗パターン**: 今後迎える各メンバーで同じ齟齬が再生産される。あるいは逆に「Gen と書いてあるが全員の意味だろう」という文言の拡大解釈が常態化し、境界文書の文言が信用されなくなる。
- **緩和策**: Q1 を Q2 と同様に「全エージェント」に一般化するか、role ごとの許可表(誰が・どこに・何を)に変える。人間の承認事項(Q1 の拡張)として growth-log に記録する。
- **判断**: **採用**(2026-07-05 人間)。Q1 を全エージェントに一般化(現規模で許可表は過剰)→ base-fix-draft.md 変更3・4

### P1-2: team.md は「Rin レビューなしの提案は不完全」と言うが、workflow.md の基本フローに Rin が存在しない

- **対象**: team.md Rin 節「Rin のレビューがない提案は最終提案として不完全である」/ workflow.md ヘッダ「対象範囲: 人間 ⇄ Gen だけの最小フロー(チームが Gen 一人の間)」と1節の基本フロー(Rin のステップなし)/ roadmap.md Stage 4「5人そろったら workflow.md を…標準フローに更新」/ team.md 原則「No Consensus Without Dissent …(Rin 加入後に本格運用)」
- **指摘**: Rin は加入済みだが、workflow.md の更新契機は「5人そろったら」(Stage 4)のまま。つまり Stage 2〜3 の間、**正本の手順どおりに進めると Rin レビューを経ない提案が人間に届き、team.md の宣言と矛盾する**。さらに「本格運用」の開始条件・対象(どの成果物に Rin レビューが必須か。全部か、final-proposal だけか、正本変更ドラフトだけか)がどこにも定義されていない。
- **失敗パターン**: 小さい提案は「これは軽いから Rin 不要」と Gen と人間の二者で確定し続け、No Consensus Without Dissent が原則としては存在するのに運用としては発動しない。Rin が「名前だけ増えて出力が同じ」失敗条件(roadmap Stage 5)に、定義の欠陥のせいで陥る。
- **緩和策**: Stage 4 を待たず、workflow.md 1節に最小の一行を足す(例: 「正本 docs の変更ドラフトと final-proposal は、人間判断の前に Rin レビューを経る。それ以外は人間または Gen が必要と判断したとき」)。対象の線引き自体は人間が決める。
- **判断**: **採用**(2026-07-05 人間)。必須範囲は「正本変更ドラフトと final-proposal」(許容判断 C)→ base-fix-draft.md 変更5 / ADR 候補あり

### P1-3: Rin が P0 を付けても、プロセス上は何も止まらない

- **対象**: team.md Rin 節「P0: 取り返しがつかない・安全境界に関わる。**対応するまで先に進むべきでない**」
- **指摘**: P0 の定義は「先に進むべきでない」と言うが、workflow.md にも safety.md にも「P0 指摘が出たら何が起きるか」の手順がない。人間が risk-review.md を読み飛ばしても、Gen が要約で丸めても、フローは止まらない。重大度スキームが**表示上のラベルであって制御ではない**。AIが進行を止める権限を持つべきではない(人間が最終判断者)が、「人間が明示的に却下するまでは先に進まない」程度の握りは必要。
- **失敗パターン**: P0 指摘が current-task の次ステップに追われて未判断のまま滞留し、数 Stage 後に「あのとき指摘は出ていた」だけが残る。責任を記録に持たせる設計(team.md 原則)が、記録はあるが判断がない状態を生む。
- **緩和策**: workflow.md に一行追加: 「Rin の P0/P1 指摘は、人間が採用 / 却下 / 保留を**明示的に**判断し、その結果を risk-review.md の該当項目に記録するまで、当該対象の確定・Stage の完了をしない」。却下は正常(team.md どおり)。判断の記録だけを義務にする。
- **判断**: **採用**(2026-07-05 人間。許容判断 D: 進行速度の低下を受け入れる)→ base-fix-draft.md 変更6 / ADR 候補あり。本記録自体がこのルールの初適用

### P1-4: 未コミット作業の喪失に対して無防備(jj 全面禁止 × 上書きは削除禁止の対象外 × コミット時機の規定なし)

- **対象**: safety.md 2節「`jj describe` / `jj new` / `jj commit` を含む**すべての jj 操作**は常に人間が行う」「ファイル・ディレクトリの削除、リネーム・移動による実質削除をしない」/ workflow.md 2節「バージョン管理(jj / git)の操作は常に人間が行う」
- **指摘**: 三つの規定の組み合わせに穴がある。(1) 削除は禁止だが **Write による全面上書きは禁止に該当しない**。(2) コミットは人間のみだが、**いつコミットするかの規定が workflow.md のどこにもない**(基本フロー7ステップにも記録の使い分けにもない)。(3) 禁止が「すべての jj 操作」なので、エージェントは `jj st` / `jj diff` すら実行できず、**いま失われうる未コミット差分があるかを確認する手段がない**。結果: 人間のコミットが遅れている間に、エージェントが善意の上書き(例: current-task.md の更新、risk-review.md の再生成)で復元不能に前版を消せる。この文書群は成果物がすべての設計なので、成果物の喪失はチームの記憶喪失に等しい。
- **失敗パターン**: セッションまたぎで Gen が current-task.md を「最新化」し、人間が未コミットだった前セッションの完了条件チェックが消える。誰も禁止事項に違反していない。
- **緩和策**: 少なくともどちらか一つ。(a) workflow.md 1節に「人間はセッションの区切り(handoff-log 追記時)にコミットする」を明記し、Gen の責任に「大きな上書きの前に、人間に未コミット差分がないか確認を促す」を足す。(b) 読み取り専用の jj 操作(`jj st` / `jj diff` / `jj log`)のみ許可に緩和する。(b) は safety.md の緩和なので「人間の明示承認 + growth-log 記録」(safety.md ヘッダ)を要する。禁止の趣旨(履歴改変の防止)は読み取りでは損なわれない、が判断は人間に委ねる。
- **判断**: **(a) 採用**(2026-07-05 人間)→ base-fix-draft.md 変更7・8。**(b) は明示確認待ち**(許容判断 B。safety 初緩和のため包括承認では反映しない)

### P1-5: アダプタは「存在する」だけで「機能する」ことが未検証のまま完了扱い — 実際に本セッションで機能しなかった

- **対象**: roadmap.md Stage 2 の手順(「`.claude/agents/rin.md` を作成」→ 次が「試運転」で、アダプタ経由の起動確認という工程がない)/ 参考: current-task.md 6節「[x] .claude/agents/rin.md(薄いアダプタ)が人間承認を経て**存在する**」
- **指摘**: 現に本セッションの Rin は、アダプタが同一セッション中の作成で未認識だったため、**アダプタ経由ではなくプロンプトへの手書きインライン展開で起動された**。完了条件が「存在」であって「アダプタ経由で起動し、正本を読んで振る舞う」ではないため、この失敗はチェックリスト上は見えない。さらにインライン展開は、アダプタと中身が一致している保証がなく(今回は「同内容 + 詳細」と注記されたが検証手段は Rin 側にない)、**正本 → アダプタ → 実際の起動指示、と写しが増えるほどドリフトする**構造リスクがある。これは以降全メンバーに適用される「標準手順」になる予定であり、いま直さないと4回再生産される。
- **失敗パターン**: 将来メンバーのアダプタが古い定義のまま残り、team.md を更新したのにサブエージェントの振る舞いが変わらない。「名前だけ増えて出力が同じ」失敗条件の技術的な発生経路。
- **緩和策**: roadmap Stage 2(= 標準手順)の完了条件に「新しいセッションでアダプタ経由の起動が確認できた」を追加。アダプタには詳細を書かず正本参照のみに保つ現方針は正しい(維持)。インライン起動で代替した場合は handoff-log にその旨と乖離リスクを記録する。
- **判断**: **採用**(2026-07-05 人間)→ base-fix-draft.md 変更9。rin.md アダプタは次セッションで起動検証する(current-task に記載)

### P1-6: 「必ず反対意見を出す」設計は、反対の量産と重大度インフレを構造的に招く(Rin 自身の定義への指摘)

- **対象**: team.md Rin 節「反対意見・失敗パターン・見落としを**必ず**出す」「合意を丸めて指摘を引っ込める(指摘が却下されるのは正常。**出さないのが異常**)」/ roadmap.md Stage 2 完了条件「Rin が一般論ではない具体的な反対意見を出せている(出せていなければ定義を直すか、迎える順序を再検討)」
- **指摘**: この定義には「**重大な問題は見当たらない**」という出力が正当な結果として存在しない。しかも Stage 2 の完了条件と Rin の存続(「出せていなければ…迎える順序を再検討」)が「反対意見が出ること」に懸かっており、**Rin は自分の存在価値を賭けて反対を生産するインセンティブを持つ**。この risk-review 自体がその圧力の下で書かれていることを、読む人間は割り引くべきである。放置すると、指摘の水増し・P2 の P1 化・毎回同じ懸念の再掲が起き、人間が重大度ラベルを信用しなくなる(狼少年化)。それは「都合の悪いリスクを丸める」の逆側から同じ結果(重大度シグナルの死)に至る。
- **失敗パターン**: 数 Stage 後、人間が「Rin の P1 はいつものやつ」と読み流すようになり、本物の P1 が通過する。
- **緩和策**: team.md Rin 節に2点追記する。(1) 「対象を検討した観点の一覧を添えたうえで『重大リスクなし(P2 のみ / ゼロ)』と報告することは、正当な成果である」(2) 「同一対象への再指摘は、前回からの差分がある場合のみ」。評価軸を件数ではなく「指摘が反証可能・対象特定可能か」に置く(Stage 2 の判定でも件数を評価基準にしないでほしい)。
- **判断**: **採用**(2026-07-05 人間。許容判断 E: 観点一覧の添付を条件に「重大リスクなし」を正当な出力と認める)→ base-fix-draft.md 変更10 / ADR 候補あり

## 3. 改善余地・将来の火種(P2)

### P2-1: 「作業用一時ファイルを除く」の境界が未定義

- **対象**: safety.md 2節「リポジトリ外への書き込み・外部サービスへの送信をしない(**作業用一時ファイルを除く**)」
- **指摘**: 例外の範囲が定義されていない。文の構造上、例外が「外部サービスへの送信」側にも掛かると読める余地すらある。どこまでが一時ファイルか(OS の temp / セッションの scratchpad / ~/ 直下?)、中に何を書いてよいか(リポジトリ内容の丸写しは?)が読み手任せ。
- **緩和策**: 「セッション用 scratchpad と OS の一時領域に限る。外部サービスへの送信に例外はない」と一文で限定する。

### P2-2: Rin に「緩和策なしの否定禁止」を課しつつ「対策の設計は Kai の領域」とする境界の緊張

- **対象**: team.md Rin 節「代替案・緩和策なしに否定だけする」(禁止)と「対策の設計は Kai、検証の設計は Toki の担当領域」
- **指摘**: Kai・Toki 不在の現在、Rin の緩和策はどこまで踏み込んでよいのか、加入後はどう線を引くのかが曖昧。踏み込みすぎれば Rin が設計者を兼ね(レビューの独立性が落ちる)、控えすぎれば禁止事項に抵触する。
- **緩和策**: 「Rin の緩和策は方向性の提示まで(採用可能な選択肢があることを示す水準)。詳細設計はしない」を Rin 節に一文追記。Kai 加入時に再確認。

### P2-3: 「調査は仮説を人間に説明してから」はサブエージェントには実行不能

- **対象**: workflow.md 7節「調査は仮説から: …必ず先に仮説を立て、**人間に仮説を説明してから**作業する」(2026-07-05 人間提案。**全エージェントに適用**)
- **指摘**: サブエージェント(Rin 含む)は実行中に人間と対話できない。全エージェント適用と明記された規則が、サブエージェントには文字どおりには守れない。守れない規則を置くと「規則は建前」という学習が全規則に波及する。
- **緩和策**: 「サブエージェントは、仮説を成果物の冒頭(前提節)に明記することで代える」を7節に追記。本レビューも前提節を置くことで趣旨に沿わせた。

### P2-4: 正本の置き場に直接ドラフトを作れる規定は、状態行を確認しない読者に未承認内容を確定として読ませる

- **対象**: workflow.md 3節「新規の正本ファイルは、冒頭に『状態: ドラフト(人間承認待ち)』と明記したうえで、置くべき場所(例: docs/agent/)に直接作成してよい」
- **指摘**: 読み手(特に「team.md と safety.md を読め」とだけ指示された将来のサブエージェント)が状態行を検査する義務はどこにも書かれていない。docs/agent/ にあるという事実が「確定」のシグナルとして機能してしまう。承認待ちの safety 緩和ドラフトが、承認前に事実上運用される経路になる。
- **緩和策**: どちらか。(a) アダプタ・AGENTS.md に「正本を読むときは状態行を確認し、ドラフトは確定として扱わない」を一文追加。(b) ドラフトはファイル名で区別する(例: `*.draft.md`)。(b) の方が読み手の注意力に依存しない。

### P2-5: ADR ドラフトが既に8件滞留しており、レビューの時機が定義されていない

- **対象**: workflow.md 6節(ドラフト作成の時機・粒度はあるが、人間レビューの時機がない)/ 参考: current-task.md 7節「(急がない・Stage 1 からの持ち越し)ADR 候補のドラフト内容確認と昇格対象の選択(計8件)」
- **指摘**: 「同じセッション内でドラフトを作る」ルールは生産側だけを規定しており、消費側(人間の判断)の cadence がない。土台づくり2 Stage 目で既に8件未判断。このペースだと Stage 5 到達時に数十件になり、「後から Why を辿れる」はずの ADR が、未判断の山として逆に信頼できない記録になる。
- **緩和策**: workflow.md 6節に「Stage の節目に、滞留ドラフトの昇格 / 却下 / 保留をまとめて判断する」を追加。件数が多ければ Gen が判断しやすい一覧(推奨付き)を作る。

### P2-6: Stage 2 の完了判定を、この risk-review 単体で行うことの利益相反

- **対象**: roadmap.md Stage 2 完了条件「Rin が一般論ではない具体的な反対意見を出せている」
- **指摘**: P1-6 の派生。判定材料が「Rin が自分の合格のために書いた文書」1点である。1回の出力での合否は、サブエージェントの出力分散(同じ定義でも回によって質が揺れる)も拾えない。
- **緩和策**: 判定は本レビューで仮判定とし、次の実対象(例: 次の正本変更ドラフト1件)への2回目のレビューで確定する。判定基準は件数でなく「指摘が対象特定可能で、人間が採用 / 却下を判断できたか」。

### P2-7: 全禁止事項が指示ベースで、技術的強制と記録の完全性の担保がない

- **対象**: safety.md 全体(特に2節の jj / git 禁止)/ AGENTS.md「メイン会話は、作業を始める前に必ず…読むこと(MUST)」/ safety.md 4節「.ai/board/ 配下の記録…の**追記**」
- **指摘**: 最重要の禁止(Q2)も MUST 読み込みも、エージェントが指示に従う前提の紙の壁である。Claude Code には permissions(deny ルール)や hooks による技術的強制があるが使われていない。また .ai/board/ は「追記」のみ許可だが、既存エントリの改変禁止が明文化されておらず、「責任を記録に持たせる」(team.md 原則)割に記録の完全性は善意頼み。現規模では許容可能だが、メンバーとセッションが増えるほど一点の逸脱が検出不能になる。
- **緩和策**: (a) .claude/settings.json に `jj` / `git` の deny ルールを入れる(これ自体を正本扱いにする — P0-1 と同時に対応)。(b) safety.md 4節の「追記」に「既存エントリの改変・削除はしない」を明記。いずれも人間承認事項。

## 4. 楽観的前提への反論(横断)

1. **「薄いアダプタ + 正本参照で、サブエージェントは定義どおり動く」** — 本セッションで既に破れた(P1-5)。写しの層が増えるほどドリフトは既定であって例外ではない。
2. **「禁止事項を正本に書けば守られる」** — 守られるのは読まれた場合であり、読む義務の伝播(AGENTS.md → サブエージェント)と技術的強制の両方に穴がある(P0-1, P2-7)。
3. **「人間がコミットするから履歴は安全」** — コミットの時機が規定されていない以上、未コミットの窓は常に開いている(P1-4)。
4. **「Rin を入れたので楽観合意は防げる」** — フローに組み込まれていない反対役は、いるだけでは機能しない(P1-2)。むしろ「Rin がいる」という事実が安心材料として楽観合意を強化しうる。
5. **「指摘が出たから健全」** — 指摘は判断されて初めて機能する。判断の義務がなければ、リスクレビューはアリバイ文書になる(P1-3)。

## 5. 人間が許容判断すべきリスク

以下は「直す」ではなく「飲むかどうかを決める」もの。飲む場合はその旨をどこかに記録してほしい(暗黙に飲まされる状態の解消が目的)。

| # | 許容判断の内容 | 関連 |
|---|---|---|
| A | **禁止事項を指示ベース(紙の壁)のまま運用するか、技術的強制(deny ルール等)を入れるか**。現規模なら紙でも回るが、逸脱の検出手段はない | P0-1, P2-7 |
| B | **読み取り専用の jj 操作をエージェントに許すか**。許せば喪失防止に効くが、safety の初緩和になり前例が生まれる | P1-4 |
| C | **Rin レビューの必須範囲**をどこに引くか(全提案 / 正本変更と final-proposal のみ / 都度指定)。広いほど安全で、遅くなる | P1-2 |

| E | **「重大リスクなし」を Rin の正当な出力として認めるか**。認めれば狼少年化を防げるが、Rin が楽をする経路にもなる(観点一覧の添付を条件にすることで緩和可能) | P1-6 |
