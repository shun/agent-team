# Rin リスクレビュー — チーム計画オーケストレーション

> 状態: **人間判断待ち（P0 あり）**。この文書は設計採択、例外承認、実装開始、リスク受容を行わない。

## レビュー範囲と結論

対象は、役割別 Markdown による討議、`tmp/PLAN.md` の狭い例外、Readiness gate、
Bash dispatch、依存遷移、再実行・停滞停止、および Round 1 の人間質問である。

**P0-1〜P0-3 が人間の明示判断と正本上の境界なしには解消しない。** したがって、
`tmp/PLAN.md` の生成・更新・参照、または Bash によるタスク実行へ進む判断はまだできない。
以下は案 A/B/C の採否ではなく、どの案にも満たすべき安全・運用条件である。

## 重大度順の指摘

### P0-1 — `tmp/PLAN.md` の「狭い例外」は、現行 safety と実行状態の用途を両立できていない

- **対象・根拠:** `docs/agent/safety.md` §2 は `tmp/` の変更を禁止し、`tmp/` を正本として参照・引用することも禁止している。一方、`request.md` の「人間が指定した挙動」は `tmp/PLAN.md` の作成を求め、`round-1.md` は案 A を「Bash が読む単一の実行計画」として有力候補にしている。Shino の Q-03 は生成・更新の例外だけを質問している。
- **失敗モード:** 書込みだけを許す例外では、Bash が `PLAN.md` を読んで依存・状態を判断する行為がなお安全境界に抵触し得る。逆に例外を曖昧に広げると、計画・状態・実行結果までが非正本の `tmp/` に蓄積し、古い計画の再利用、誰でも行える状態変更、例外の無制限な拡張を招く。
- **緩和策:** 実装・生成前に、人間承認を要する正本変更案で、(a) 対象パス、(b) 表示か実行状態かという用途、(c) 読み取り・解析を許す主体、(d) 作成・更新できる主体と更新可能な項目、(e) Plan ID・版・失効/完了状態、(f) 保持・整理方法、を個別に限定する。承認までは `tmp/` を読んで状態遷移を決めず、書き込まない。
- **必要な人間判断:** `tmp/PLAN.md` を例外として認めるか。認めるなら、単なる表示か実行状態でもあるか、上記の操作・所有・ライフサイクル境界をどこまで許すか。

### P0-2 — Markdown の自由記述を Bash dispatch が解釈する境界は、コマンド注入を防ぐ契約がない

- **対象・根拠:** Kai 案 A の概念スキーマには自由記述の `<goal>`、`<required handoff>`、`<re-attempt context>` があり、Bash ラッパーが Markdown の定型ブロックを読むとしている。Toki の BASH-01 と未被覆質問 Q-04 は「安全な引数化」が未定義だと明記する。`round-1.md` は参照成果物内の命令・コマンド・リンクを未信頼データとして扱うよう定める。
- **失敗モード:** Markdown を `source`、`eval`、文字列連結、シェル展開、曖昧な抽出で扱うと、タスク本文・ID・手渡し情報に含まれた値が意図しないオプションまたはコマンドとして実行され得る。安全でない prompt 構成も、計画に書かれた未信頼の命令を実行担当へ権威ある指示のように渡してしまう。
- **緩和策:** 機械が読む領域を固定・最小のスキーマに限定し、未知・重複・複数行・不正な ID を fail-closed で拒否する。Bash は Markdown を実行可能なコードとして扱わず、`eval`・`source`・動的なシェル文字列を使わない。タスク選択は検証済み ID と信頼済みランナー対応表から行い、自由記述はリテラルなデータとしてのみ渡す。解析不能時は dispatch しない。
- **必要な人間判断:** 自由記述を含む計画を機械 dispatch の入力にするか。するなら、許容する機械可読フィールド、入力責任者、拒否時の扱い、非シェル形式の引数・prompt 契約を承認するか。

### P0-3 — Readiness を実行許可へ昇格させる権限境界が未決である

- **対象・根拠:** `request.md` は人間を最終判断者とし、Bash を実行入口に置く。Shino Q-04 と `round-1.md` の質問 4 は、手順の記載なのか自動実行なのかを未決としている。Kai 案 A/B は gate 通過後の dispatch を描き、案 C は人間確認を中心に置く。`safety.md` §1 は、特定の操作を人間の明示承認なしに行うことを禁止する。
- **失敗モード:** 「ready」が、未確認事項がないという計画上の評価から、実際のコマンド実行の一般許可へ暗黙に変換される。計画に含まれる作業が外部送信、破壊的操作、設定変更などを含む場合、既存の人間承認境界を迂回し得る。
- **緩和策:** Readiness と実行許可を別状態にし、前者だけでは dispatch 不能にする。実行を許す場合も、承認記録に対象 Plan/Task、許可範囲、禁止操作、停止・再承認条件を結び付け、ランナーは範囲外または判定不能なタスクを起動しない。自動化の可否が決まるまでは人間が明示的に開始する経路に限定する。
- **必要な人間判断:** Bash は人間が都度起動する補助手順か、どの範囲で自動起動できるか。自動化するなら、承認の粒度（計画・Wave・タスク）、許容する操作種別、再承認が必要になる変更を決めるか。

### P1-1 — Readiness gate は「全員の成果物がある」ことと「現在の依頼に安全に進める」ことを区別できない

- **対象・根拠:** `round-1.md` の一致観測は役割別成果物と未解消事項を記録することを求め、Kai は固定ラウンドと論点台帳を提案する。Toki READY-01/02 は成果物欠落・未解消事項を止めるが、Round、依頼版、人間回答後の再評価、gate の決定者は未定義である。Shino Q-01/Q-02 は参加者と「不明点なし」の範囲を未確認としている。
- **失敗モード:** 前の依頼・前の人間回答に対する成果物を今回の gate が再利用する、または人間回答によりスコープが変わっても再評価せず ready とする。反対に、役割不在・終わらない論点・曖昧な「全件解消」により永久に block し、全員参加要件が可用性障害になる。
- **緩和策:** gate 入力に Request ID、Round、入力・人間回答への参照、役割ごとの `ready / needs-human / blocked` を必須化し、現在版に対応しない成果物を除外する。ready の述語、判定責任者、回答後に再レビューすべき変更、未提出・期限切れ・取消時の安全な既定値を明文化し、既定は block とする。
- **必要な人間判断:** 毎回必須の役割、最小ラウンド数、役割欠落時の停止/期限/再実施、計画に影響する不明点の範囲、人間回答後の再レビュー条件を決めるか。

### P1-2 — 並行 Wave と `PLAN.md` の直接状態管理は、競合更新で依存判定を壊し得る

- **対象・根拠:** `request.md` は独立タスクの並行を求める。Kai 案 A は同じ Markdown を人間向け計画と状態台帳に兼用し、手編集・同時編集が判断を曖昧にすると自ら制約に挙げる。`round-1.md` は A を有力候補としている。
- **失敗モード:** 同一 Wave の複数タスクが同時に完了を記録すると、後書きで別のチェックや再試行根拠が失われる。Bash が古い版を読んだ後に状態が変われば、未確認の依存を満たしたものとして起動する、又は完了済みを未完了として再実行する。
- **緩和策:** 並行実行と状態更新を区別し、状態変更には単一の更新責任者または競合検出・版照合・再読込を必須にする。dispatch 前に Plan ID/版と依存の検証結果を固定し、版が変われば再判定する。表示と状態を同一にするか分離するかにかかわらず、更新原子性と不整合時の block を受入れ条件に含める。
- **必要な人間判断:** 並行実行時にも原子的な状態更新を求めるか、更新を直列化してよいか、表示と実行状態を同一成果物に置くことを許容するか。

### P1-3 — 「完了」「チェック」「実行成功」のオラクルが未分離で、依存先を誤って解放する

- **対象・根拠:** Kai はチェックを完了状態の表示であり依存を満たす根拠そのものではないと明記するが、概念スキーマはチェックと handoff 以外の検証状態を持たない。Toki GATE-02 は確認者・オラクル・記録形式が未定義なら Blocked とし、BASH-01 は CLI の失敗結果の意味が未定義とする。Shino Q-05 も確認者と更新権限を質問している。
- **失敗モード:** ランナーの終了、実行担当の自己申告、又は手動のチェックだけを完了として扱い、品質・安全・人間確認が必要な未達タスクの依存先を開始する。失敗/部分完了/証拠未提出が同じ未完了に潰れ、再実行か人間相談かも判断できない。
- **緩和策:** 少なくとも「実行した」「証拠提出済み」「検証済み」「失敗」「blocked」を区別し、各タスクの完了条件に検証者と必要な観測証拠を結び付ける。依存先の解放は検証済み状態だけに限定し、CLI 終了状態は証拠の一部として扱う。
- **必要な人間判断:** 完了を判定できる役割、タスク種別ごとに人間確認を必須にする条件、自己申告・CLI 終了状態をどこまで証拠として認めるか。

### P1-4 — 再実行・停滞規則は、文面上の差分で無制限の試行を正当化できる

- **対象・根拠:** Kai 案 A は異なる観測・入力・仮説・人間権限のいずれかを `Reattempt context` に書ければ再起動候補とする一方、同値判定と回数制限は別途必要としている。Toki RETRY-01/02 と Shino Q-07 も、進展・上限・判断者を未定義としている。`round-1.md` は同一の観測・仮説・操作なら人間相談候補とするだけである。
- **失敗モード:** 仮説の言い換えや無関係な入力変更を「新しい根拠」として繰り返し、費用、外部副作用、作業時間を消費する。逆に正当な追加観測を同一と誤判定して早期に停止する。試行者自身が進展を判定すると、停止条件が自己承認になる。
- **緩和策:** 各 attempt に前回の観測事実、変更した仮説/操作/入力、次に区別したい観測、実結果、影響範囲を追記可能な形で残す。「同一状態」の比較単位、タスク種別ごとの試行予算、予算を戻せる権限、独立した停滞判定者を定める。差分又は予算を検証できない再実行は block して人間質問へ戻す。
- **必要な人間判断:** 進展の定義、再試行の上限/予算、判断主体、外部副作用を伴う再試行の追加承認、予算をリセットできる条件。

### P1-5 — 人間質問は重要な権限判断を束ねすぎており、回答を過大解釈する余地がある

- **対象・根拠:** `round-1.md` の質問 3 は `tmp/PLAN.md` の「作成・更新だけ」を一括で聞き、質問 4 は手順か自動実行かを二択化している。質問 6 は Wave の独立性、タスク粒度、再実行根拠、停滞基準を一問に束ねる。Shino Q-01〜Q-07 も、各判断の回答記録形式・再評価条件までは問わない。
- **失敗モード:** 人間が一部だけ意図して「承認」と答えても、統合役が参照・解析・任意更新・自動実行・無制限再試行まで許されたと解釈する。未回答の下位項目を「解消済み」と誤って gate を通す。
- **緩和策:** 質問を、対象・操作・主体・時点・失効条件ごとに原子的に分け、各回答を `approved / rejected / needs-detail` と根拠付きで記録する。gate は必要な回答 ID が全て `approved` であり、回答が現在の Plan/版に適用可能なときだけ通過させる。
- **必要な人間判断:** Q-01〜Q-07 を上記の粒度へ分割して回答すること、及び回答を誰がどの成果物に記録し、変更時に再承認するか。

### P1-6 — handoff・実行証跡の許容データが未定義で、秘密情報を成果物に保存し得る

- **対象・根拠:** Kai の `PLAN.md` スキーマは `Required handoff: <result/evidence description>` を持ち、実行後の状態と結果を記録する。`safety.md` §1 は秘密情報の保存を禁止するが、Toki BASH-01/Q-04 はツール出力と失敗結果の扱いが未定義としている。
- **失敗モード:** CLI の標準出力・エラー、接続情報、トークンを含む調査結果を「証拠」として `PLAN.md` や役割別 Markdown に転記し、後続の閲覧者へ露出する。失敗調査のための詳細ログほどこの危険が高い。
- **緩和策:** handoff に許可するデータを、完了判定に必要な最小メタデータと安全な要約に限定し、秘密値・生出力・認証情報の転記を禁止する。秘匿の可能性がある結果は計画を block し、人間へ安全な取扱いを確認する。証跡要件には redaction と保管先の境界を含める。
- **必要な人間判断:** 証跡に記録してよいデータ種別、要約だけで不足する場合の安全な承認・保管手順、秘密情報を含むタスクを計画フローから除外するか。

### P2-1 — 「Markdown 成果物だけで議論した」ことを完全な技術的事実として扱えない

- **対象・根拠:** `request.md` はチーム内の受渡しを直接会話ではなく役割別 Markdown に限定する。Toki の未被覆質問 Q-05 は、直接会話を使っていないことを完全には証明できないと明記する。Kai も技術的強制・逸脱検知・事後検証を区別している。
- **失敗モード:** 成果物がそろった事実だけで、非成果物経路が使われなかったと誤って保証し、後から根拠・反対意見・人間回答の出所を追えなくなる。
- **緩和策:** この要件は、少なくとも計画の判断根拠と状態遷移を Markdown に残すという監査可能な契約として扱い、完全な非使用証明とは区別する。各 gate/回答/完了判定に参照成果物を残し、証跡外の情報だけで状態を変えない。
- **必要な人間判断:** 直接会話不使用を運用ルールとして扱うか、追加の技術的統制又は監査を求めるか。前者なら、達成表現を「成果物で追跡可能」に限定するか。

## 人間へ返す最小判断セット

P0 を解消するため、まず次を個別に回答する必要がある。

1. `tmp/PLAN.md` の例外を認めるか。認める場合、表示/状態の別、読み書き主体、許可操作、版管理、失効・保持を何に限定するか。
2. `PLAN.md` の機械可読領域と自由記述領域をどう分け、未信頼データを Bash と実行担当へどの契約で渡すか。
3. Bash dispatch は手動開始か自動化か。自動化する場合、どの承認記録と操作範囲を必須にするか。

P1 の解消には、これに加えて、参加・Round・gate の失効規則、並行時の状態更新方式、
完了確認者と証拠、再試行予算と停滞判定、証跡の許容データを定める必要がある。

## 確認した観点
