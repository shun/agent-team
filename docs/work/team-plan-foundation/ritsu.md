# Ritsu 実行可能性レビュー

この成果物は、Round 1 の候補を実行担当の観点から評価する。設計の採否、
オラクル、リスク受容、最終合否は決めない。ここでいう「強制」は、管理された
入口で条件を満たさない遷移を起動前に止められること、「検知」は、違反または
判定不能を証跡として識別できることを指す。

## 結論

現入力だけでは、5項目をすべて技術的に強制できるとは言えない。Bash ガードは、
単一の管理入口、機械可読な状態、競合防止、対象範囲内の書込み隔離が人間により
固定された場合に限り、起動前の依存検査・チェック検査・機械的な再試行停止を
強制できる。それ以外の経路を閉じられない場合、ガードは違反を検知する補助で
あり、実行済みの逸脱を防いだとは報告してはならない。

| 対象 | 管理入口で強制できる範囲 | 強制できず検知に留まる範囲 |
| --- | --- | --- |
| 依存完了 | 依存 ID が存在し、各依存の状態が `completed`、完了証跡参照があり、計画版が一致する場合だけ起動を許可する。循環・欠落・未チェックを起動前に止められる。 | 完了条件そのものの真実性、外部作業の完了、人手による虚偽の完了記録、ガード外の直接起動。完了オラクルと状態更新者が未定義なら判定不能である。 |
| チェック更新 | 完了証跡の確認とチェック更新を同一の管理された状態遷移にし、順序と対象 ID を検査できる。未確認のチェック更新を拒否する設計は可能である。 | Markdown のチェック記号だけでは完了を証明できない。任意編集、並行編集、ガード外の更新、確認者の権限は、所有者・排他・履歴がなければ検知に留まる。 |
| ランナー失敗 | ランナーの起動失敗、非ゼロ終了、シグナル終了、タイムアウトを取得し、依存先を停止する遷移は強制できる。 | `codex exec` / `agy -p` の実際の失敗意味、子プロセスが隠した失敗、成果物の内容の正しさ、ラッパーを迂回した起動は、終了値だけでは保証できない。 |
| 再実行証拠 | 前回試行 ID・結果参照・変更された入力または仮説・次に観測する条件を必須フィールドにし、同一 fingerprint や空の差分を拒否できる。 | 「新しい証拠」「根拠が十分」「仮説が有効」という意味的な真実性は機械的に証明できない。記録の存在・差分・形式を検査し、内容の妥当性は人間または担当の確認へ戻す。 |
| 停滞エスカレーション | 明示された同一 fingerprint、試行上限、タイムアウトを検知し、起動を止めて `blocked` と相談成果物を要求できる。 | 進展の意味、相談先、相談の受領、回答後の再開承認が未定義なら強制できない。数値上限や判定基準が未承認の現状では、無制限反復を安全に許可してはならない。 |

したがって、候補 A の `PLAN.md` 直読みによるガードは、構文が固定され、単独の
実行入口であることを前提にした「条件検査」としては成立候補である。しかし、
Markdown の手編集や直接 CLI 起動を許す限り、全体の安全強制ではなく検知と差戻し
である。候補 B でも状態の正本、同期、所有者、入口排他が未承認なら結論は変わら
ない。候補 C は明示的に助言型なので、依存違反・未チェック遷移・反復の強制を
主張できず、検知と人間運用の基準線として扱う。

## 実行契約に固定すべき入力

`PLAN.md` を作る前に、次の値を契約の入力として固定し、欠落・曖昧・版違いなら
実行可能と判定しない。R-01 から R-08 の要求だけでは、これらの一部は未確定で
あり、Q-01 から Q-07 の人間回答または承認済み設計が必要である。

- 計画 ID、計画版または基準版 hash、ready 判定の成果物参照、未解消質問の状態。
- タスク ID、ゴール、観測可能な完了条件、所有者、完了確認者、許可された次状態。
- 依存 ID、Wave、依存の完了に必要な証跡参照、同時実行の境界、循環検査の規則。
- チェック更新の権限、更新前に必要な完了確認、更新理由、競合時の扱い。
- dispatch 種別（`codex` または `agy`）、安全に分離された引数、対象タスク ID、
  ランナーのタイムアウト、終了値・シグナル・起動失敗の意味。
- 試行 ID、前回試行の結果参照、次の仮説、変更点、期待する観測、再試行上限、
  同一性 fingerprint、停滞時の相談先と再開権限。
- 許可された直接・間接 write 集合、証跡の保存先、対象作業コピーまたは同等の
  write 隔離、競合検査、復旧主体。エージェント dispatch を含む場合は、固定された
  agent、model、effort、fresh 性と、利用不能時に fallback しない規則も含める。

特に「完了条件を満たした」のオラクル、「進展」の定義、チェック更新者、数値上限、
人間確認後の再開者が未定義のままでは、ガードは値の存在を確認できても、実行を
安全に許可する根拠を持たない。

## write 境界と証跡

今回のレビューの write allowlist は新規の `docs/work/team-plan-foundation/ritsu.md`
だけであり、`tmp/`、正本 docs、設定、コード、テスト、VCS、外部サービスへは
書き込まない。将来の実装で `tmp/PLAN.md` を更新する場合も、現行 safety の禁止を
自動的に解除するものではなく、人間承認による狭い例外、対象所有者、基準版、
write 前競合停止、独立差分確認、復旧主体を先に固定する必要がある。

実行時に許可される write は、承認済みの計画・状態・結果・相談成果物の集合に
限定する。Bash 自体や子エージェントが暗黙に別ファイルを更新してはならない。
各起動は少なくとも次の証跡を残す必要があるが、保存場所と保持・改ざん防止は
人間が設計として決める。

- 起動前の計画 ID・版 hash、対象タスク、依存状態、チェック状態、readiness 判定。
- 判定結果（許可または `blocked`）、理由、検査時刻、競合検出、実際にランナーを
  呼んだかどうか。未起動も明示する。
- 正規化した runner 種別と引数、開始・終了、終了コード、シグナル、タイムアウト。
  秘密情報や未許可の自由入力を証跡へ複製しない。
- 結果成果物のパスまたは識別子、完了確認者、チェック更新の時系列、状態遷移理由。
- 再試行では前回結果参照、観測事実、仮説・操作の差分、期待観測、fingerprint、
  上限判定。停滞時は相談先、相談内容、`blocked` 状態、再開権限を記録する。

これらの証跡が取得できない場合、Pass や「強制済み」とせず、検知不能または
`Blocked` と報告する。証跡の存在だけでは、完了や進展の内容が正しいことの証明に
ならない。

## 停止・差戻し条件

次のいずれかに該当したら、推測や自動的な再実行をせず `blocked` として上流へ
戻す。相談内容は観測事実、影響、最小質問を分離する。

- Q-01 から Q-07、または安全境界・正本方針・`tmp/` 例外に関する人間判断が未回答。
- 必須成果物、readiness 判定、計画版、タスク ID、依存、Wave、完了条件のいずれかが
  欠落・曖昧・版不一致である。
- 完了オラクル、確認者、チェック更新権限、依存検査と起動の時系列を観測できない。
- write 隔離、基準版、競合停止、復旧主体、許可 write 集合を固定できない。
- `codex exec` / `agy -p` の引数、起動失敗、終了値、タイムアウトを安全に識別できない。
- ランナーが非ゼロ終了、シグナル終了、タイムアウト、または結果証跡欠落となった。
- 前回結果に基づく差分のない再試行、同一 fingerprint、上限超過、または停滞判定の
  オラクル欠落がある。
- Bash 入口外の起動、未許可 write、対象版の競合、指定 agent/model/effort/fresh 性の
  不一致、または指定条件からの fallback が検知された。
- 要件、設計採否、リスク受容、最終合否を Ritsu が判断する必要が生じた。

## このレビューでの実施範囲

指定された必須正本と入力成果物を読み、設計上の成立条件を評価した。実装、Bash・
CLI の起動、テスト、VCS、ネットワーク、`tmp/` の変更、外部再試行は実施していない。
本成果物は設計候補を強制可能と承認するものではなく、上流の人間判断と承認済み
オラクルが揃うまで受け入れゲートへ転用してはならない。
