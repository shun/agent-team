# チーム計画オーケストレーション: Round 1 統合メモ

> 状態: レビュー中。設計・受け入れ条件とも人間未承認。

このメモは、Shino・Kai・Toki の Round 1 成果物を、Rin・Ritsu・Hayate が
レビューできる論点へ統合する。採否、リスク受容、正本変更、実装開始は決めない。

## ここまでに一致した観測

- 役割別 Markdown 成果物、未解消事項の人間確認、依存順、完了条件、再実行停止は、
  それぞれ別に観測・記録できなければならない。
- `tmp/PLAN.md` は現行 safety の禁止対象であり、狭い例外を人間が明示しない限り
  生成・更新できない。
- Bash ラッパーで、対象タスクと未完了依存を起動前に検査することはできる可能性がある。
  ただし、直接 CLI 実行を完全に技術的強制できるとは現時点で証明できない。
- タスクは依存グラフを持つ Wave として並べれば、表示上の順序と独立作業の並行を両立
  できる可能性がある。
- 同じ観測・仮説・操作のまま再実行することは、進展と見なさず人間相談へ戻す候補である。

## 比較対象

Kai の三案のうち、以下を次のレビュー対象とする。

| 案 | 概要 | 主な未確定事項 |
| --- | --- | --- |
| A | 固定ラウンド成果物と、機械可読な最小メタデータを含む `PLAN.md` を Bash が読む。 | Markdown 構文、`tmp/` 例外、入口の非強制境界。 |
| B | 実行状態を別の構造化ファイルに持ち、`PLAN.md` は表示にする。 | 新しい状態正本と同期責務を採用するか。 |
| C | `PLAN.md` と Bash preflight は人間確認を支援し、強制を主張しない。 | 手順逸脱をどこまで許容するか。 |

この段階では A を有力候補として扱うが、採用決定ではない。理由は、ユーザーが
指定した `tmp/PLAN.md` を単一の実行計画として保ちつつ、依存・Wave・再試行根拠を
近接して読めるためである。

## 人間判断が必要な候補

Shino と Toki の質問を、重複を除いて次の論点へまとめる。

1. 毎回必須参加する「全員」は Aira を含む7役か。欠けた場合は計画生成を停止するか。
2. 計画を止める「不明点」は、スコープ・安全・依存・完了条件・実行権限に影響するものに
   限るか。
3. `tmp/PLAN.md` の作成・更新だけを安全境界の狭い例外として明示承認するか。
4. `codex exec` / `agy -p` は人間が開始を承認した後の実行入口か。それとも計画完了後に
   自動実行してよいか。
5. 完了条件の判定・チェック更新・人間確認が必要なタスクの扱いを誰が担うか。
6. 同じ Wave の独立性、タスク粒度、再実行で必要な「新しい根拠」、進展なしの停止基準を
   どう定義するか。
