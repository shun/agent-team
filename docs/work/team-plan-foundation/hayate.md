# Hayate タスク粒度・反復境界レビュー

この文書は、チーム計画フローにおける bounded worker 向けのタスク粒度、
並行 Wave、再実行停止の境界をレビューする。設計の採否、受入れ判定、
リスク受容、実装開始は決めない。現時点では人間未承認のレビュー案である。

## 結論

タスクは、入力・担当・許可された変更範囲・期待する観測・完了条件・停止条件を
計画上で一意に固定でき、1 回の短い実行で完了または Blocked を判定できる範囲まで
分割する必要がある。これらのいずれかが未定義なら、bounded worker に渡す前に
上流へ戻す。作業量や時間だけを理由に小さいと判定してはならない。

同一 Wave に置けるのは、依存グラフ上で相互に先行関係がなく、共有する書込み対象、
状態、外部副作用、または完了判定がないことを計画から確認できるタスクに限る。
独立性を確認できないタスクは直列化するか、独立性の質問が解消されるまで停止する。

再実行は、前回の観測事実から異なる仮説、変更する入力または操作、次に確認する
観測を明示できる場合だけ候補にする。同じ入力・操作・期待結果の反復、失敗理由を
説明できない反復、完了条件や権限の不足を推測で埋める反復は unsafe/stalled として
起動せず、人間へ相談する。数値上限は入力で定義されていないため、ここでは補完しない。

## Bounded worker に渡す前の粒度ゲート

次の項目を計画の各タスクに記録し、全項目を観測できる場合だけ bounded worker の
候補とする。これは新しい仕様の確定ではなく、未定義を検出するレビュー基準である。

- **単一のゴール:** 何を達成するタスクかが一文で表せ、別の成果を同じタスクに混ぜない。
- **固定された入力:** 参照する成果物、基準版、依存タスク、必要な人間回答が識別できる。
- **限定された担当と書込み:** 担当者、直接・間接の write 集合、変更してよい出力先が固定される。
- **観測可能な完了条件:** 結果または Blocked を、指定された証跡で判定できる。
- **停止条件:** 不足入力、競合、依存未完了、期待外の結果を見たときの停止先が明記される。
- **短い一回性:** 途中で別の設計判断、追加の探索、別担当の成果物待ちが必要にならない。

上記を満たさない例は、統合・分解・人間質問のいずれかを先に行う。特に、要件、
設計、オラクル、リスク受容を worker が決めるタスクや、複数の独立目的を一度に扱う
タスクは bounded worker の対象外である。分割しても依存関係、共有 write、完了判定が
未確定なら、分割だけで実行可能にはならない。

## Wave の境界

Wave はトポロジカルな依存順を表す。先行タスクがすべて完了確認され、チェック状態が
記録されるまで、後続 Wave を起動してはならない。Wave 内の表示順は優先順を意味せず、
同時開始可能性を表すには次の条件を満たす必要がある。

1. 相互に依存参照がない。
2. 同じファイル、状態、生成物、またはその他の write 対象を変更しない。
3. 一方の成果物の内容や完了判定を、他方の開始条件としていない。
4. 失敗時の停止範囲と人間への差戻し先が、各タスクで独立に観測できる。

この条件を計画から確認できない場合は、同じ Wave に置かず、直列化または Blocked と
する。「独立」「小さい」の意味、完了確認者、チェック更新者が未定義のままなら、
Wave の採用・実行を人間質問へ戻す。`tmp/PLAN.md` の作成や安全境界の例外も、承認なし
にこのレビューから導出しない。

## 再実行と unsafe/stalled 判定

再実行記録には、少なくとも前回の結果、失敗または未達の観測、次の仮説、変更点、
期待する観測、停止条件を対応付ける。これらを記録できない再実行は許可候補にしない。

次のいずれかに該当したら、worker を再起動せず `Blocked` として人間へ戻す。

- 前回と同じ仮説、入力、操作、観測を繰り返す。
- 失敗結果から因果的に導いた変更ではなく、根拠のない別案を試す。
- 新しい観測が得られず、完了条件に近づいたことを示せない。
- 依存、書込み境界、完了オラクル、人間承認の不足を仮定で埋める必要がある。
- 前回の作業が完了したか、または実行されたかを独立に確認できない。
- 再試行上限または上限到達時の相談先が未定義で、反復を止める責任者がいない。

「新しい根拠」がある場合でも、変更点と期待する観測が前回と区別できなければ
再実行可能とは扱わない。進展の有無を判定する比較対象や回数上限は入力にないため、
実装時に補完せず、人間または統合担当へ最小質問として返す。

## 入力から確認できた未確定事項

Shino、Kai、Toki、および Round 1 の成果物から、次の事項は境界を左右するが未承認で
あることを確認した。Hayate は回答を代行しない。

- 「小さい」「独立」「進展なし」の判定定義と、再試行の数値上限・責任者。
- 完了条件の確認者、チェック更新者、確認に使う成果物または記録。
- `PLAN.md` に依存、Wave、状態、再実行根拠を一意に表す構造。
- Bash 入口の排他性、実行主体、人間承認の境界、失敗結果の扱い。
- `tmp/PLAN.md` 作成・更新を許す安全境界の範囲。

これらが決まるまで、粒度や Wave の合否、再実行回数の妥当性を判定してはならない。
最小の差戻しは、「上記の各判定を誰が何の記録で行い、未定義時にどの状態へ止めるか」
を人間が指定することである。

## 自己検証

- 読み取り対象は、指定された `request.md`、`shino.md`、`kai.md`、`toki.md`、
  `round-1.md`、および必須正本に限定した。
- 書込み対象は、この `hayate.md` の新規作成だけである。
- 実装、テスト、lint、format、VCS、ネットワーク、外部コマンド実行は行っていない。
- 完了判定、最終合否、設計採否、リスク受容は行っていない。
- 未指定の field semantics、validation、logging、behavior は追加していない。
