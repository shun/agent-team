## 1. 目的

Stage 4では一度に一人だけ迎え、最初の対象を設計担当のKaiとする。

最初のフェーズでは、Kaiの試運転テーマ「名前付きサブエージェントのread/write境界を技術的にどう強制するか」について、Shinoが要件と未確認事項を整理し、GenがKai加入・試運転へ進むための判断材料へ統合する。技術方式やKai定義はこのフェーズでは確定しない。

## 2. 対象

- 技術的強制テーマの目的、対象、非対象、制約、安全ゲート、完了条件の整理
- 読み取り可能範囲を制限または検証できることの要件化
- 書き込み可能範囲を制限または検証できることの要件化
- instruction遵守と技術的強制を区別することの要件化
- Genと人間が確認可能な証跡、名前付き起動経路、既存VCSルール、外部送信禁止の要件化
- 後続のKaiが運用負荷、環境依存性、回避可能性を比較できる入力の整理
- Kaiの役割定義と試運転範囲についての複数案、pros/cons、Gen推奨、Rinへ依頼するレビュー範囲の提示

## 3. 非対象

- コード、スクリプト、sandbox、権限設定その他の強制機構の実装・実行
- 特定の実装方式、ツール、製品、設計案の採用
- Kaiの役割定義、ツール別adapter、正本docsの作成・変更
- 外部サービスへの接続・送信、リポジトリ外への書き込み、高権限操作

- Stage 4の完了判定

## 9. 人間判断の報告ルール（Stage 4で試行）

2026-07-19の人間指示により、Genは判断を求める際、質問項目だけを返さず、先に次を報告する。

1. **何を決めるか**: 今回の判断対象と、判断対象ではないもの
2. **なぜ今決めるか**: 次のどの作業・安全ゲートに必要か
3. **どう判断するか**: 人間が見る観点と判断基準
4. **Gen推奨**: 推奨案と理由
5. **選択の影響**: 採用 / 変更 / 保留で次に何が起きるか
6. **最小回答**: 「推奨案で進めて」または差分だけで回答できる形式
7. **承認に含まれないこと**: 正本変更、実装、外部操作など、別承認が必要な範囲

問題・懸念・人間判断のような1対1の対応関係は、**`問題 / 懸念 / 人間判断（Gen推奨）` の表を優先し、各セルを体言止めにする**。状態遷移・処理順序・所有関係・分岐の理解が必要な場合だけMermaid図を使う。判断サマリーは原則1ページ相当とし、要件一覧・監査表・詳細なpros/consは別の根拠資料へ分ける。人間に根拠資料の通読を前提とさせない。

運用は次のように分ける。

- 既に承認された範囲内の可逆な通常作業: Genが推奨と次の行動を報告して進め、毎回の質問で止めない
- 人間の明示承認が必要な安全ゲート・重要設計判断: 上記7項目を報告し、最小回答だけを求めて停止する
- 情報不足で方針が大きく変わる場合: Genが仮説と推奨デフォルトを示し、必要最小限だけ確認する

本ルールはStage 4の一時運用として直ちに適用する。Stage 4の振り返りで有効性を確認し、恒久化する場合は正本変更ドラフト、Rinレビュー、人間承認を経る。
