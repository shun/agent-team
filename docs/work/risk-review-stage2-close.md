## 2. 重大リスク(P1)

### P1-1: 案1 の「独立課題として切り出し」は、同じゲートが Stage 3 で再出現する事実を比較に載せておらず、切り出し先も未定義

- **対象**: 7節 案1(「未解決なのは起動経路という環境・技術問題」「current-task の残チェックを課題への参照に置き換えて Stage 2 を閉じる」)/ 案2 の cons(「Stage 3 への着手が起動経路の調査にブロックされる」)/ 9節 状態行案(「独立課題として切り出し、次セッション以降で再検証」)
- **指摘**: 2点が対になっている。
  (a) **比較の非対称**。Stage 2 の目的は「メンバーの迎え方の**標準手順を確立する**」(current-task 1節)であり、9節の注記自身が「標準手順としては以降のメンバーに引き続き適用」と書くとおり、アダプタ起動確認は Shino(Stage 3)の完了条件として**必ず再出現する**。環境問題が未解決なら案1 でも Stage 3 は Shino の完了確認で同じ壁に当たる。案1 は「着手はブロックされない」だけで「完了までに解決必須」は変わらないのに、この事実は案1 の cons に書かれず、案2 側にだけ「ブロック」と書かれている。案1 の実利(実テーマの準備を環境調査と並行できる)は本物だが、人間が「切り出し済み=もう別件」と読んで優先度を下げると、Stage 3 で不意打ちのゲートになる。
  (b) **切り出し先が未定義**。「独立した技術課題として切り出し」の置き場がどこにも指定されていない。current-task.md は Stage 3 着手で新テーマに書き換わる進捗正本であり(workflow.md 4節)、「current-task の残チェックを課題への参照に置き換える」だけでは、参照ごと次の書き換えで消える。roadmap 状態行に「次セッション以降で再検証」と書く案は、進捗を roadmap に持ち込まない一本化原則(roadmap ヘッダ・workflow.md 4節)と緊張する。
- **失敗パターン**: Stage 2 完了 → Stage 3 の current-task が新規作成され、起動経路課題への参照が引き継がれない → 数セッション後、Shino のアダプタ起動確認で初めて「そういえば直っていない」が発覚し、Stage 3 が終盤で停止する。課題は消えていないのに、記録上は誰のチェックリストにも載っていない。
- **緩和策**: 案1 を採るなら、(1) 7節 案1 の文中に「Stage 3 でも Shino の完了確認で同じ確認が必要になる(解決の実質期限は Stage 3 完了前)」を明記して比較を対称にする。(2) 切り出し先を固定する — 最小は「Stage 3 の current-task 作成時に『前提・持ち越し』節へ必ず記載する」を 9節に書き添えること。より確実なのは roadmap Stage 3 の「迎える契機」に「アダプタ起動経路の解決を Shino 迎え入れの前提とする」の一行を(同じ正本変更ドラフトの中で)足すこと。

## 5. 楽観的前提への反論(横断)

1. **「切り出せば Stage 3 は自由に進める」** — Shino の完了確認で同じゲートが標準手順として再出現する。切り出しは期限の明示とセットでなければ先送りである(P1-1)
2. **「環境起因」** — まだ仮説であり、次点原因(jj 管理で git 未認識)が正しければ原因は環境ではなく自分たちの構成判断。語の選び方が対処の所在(人間の構成判断)を隠す(P1-2)
3. **「grep で機械確認するから削除は安全」** — 確認は既に「引っかかる」ことが分かっている。安全弁の体裁を持つ手順が、実際には承認済み ADR の事後編集という新種の操作を呼び込む(P1-3)
