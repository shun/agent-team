評価計画、試験契約、ADR候補である。正本反映前の2026-07-19版を段階的に確認した。

| 段階 | 判定 | 件数 |

最終確認は正本の完成文面全体に対する新規レビューではない。人間はこのレビュー経過と

## 2. 採用済みの緩和策

人間判断と正本には、次の緩和策を反映した。

- Ritsuだけを先行し、HayateはRitsuのgrowth loop完了まで進めない
- 状態を`未加入 → docs-only試用 → コード試用 → 役割別加入`へ分ける
- Luna/highを必須とし、platform証跡がなければfallbackせず`blocked`とする
- 専門判断と受入れ確認を依頼元に残し、固定後作業だけをRitsuへ委譲する
- 初期の物理dispatch、競合調整、証跡統合をGenへ集中する
- docs-only試用を試行専用の新規`docs/work/`出力だけに限定する
- 依頼、Ritsu結果、専門レビュー、再作業結果を別ファイルへ記録する
- 再作業上限到達時は、原因を断定せず
  `契約不足 / Ritsu逸脱 / oracle不足 / platform障害`として上流へ戻す
- Gate Cを技術的write隔離と別の人間承認まで停止する

## 3. 現在の残留リスク

Ritsu単独先行の人間判断後も、次のリスクが残る。

### P0: Gate Cの技術的write境界が未実証

- 失敗パターン: 隔離方式、基準版、競合検知、差分確認者、復旧主体が曖昧なまま既存
  ファイルを更新し、他の未コミット変更または正本を上書きする。
- 緩和策: 使い捨て作業コピーまたは同等の技術的write制約を実装し、対象所有者、基準版、
  write前競合停止、独立差分確認、復旧手順を実証する。
- ゲート: いずれかを用意できない場合はGate Cを実行しない。

### P1: Luna/highの信頼できる実行証跡が未取得

- 失敗パターン: adapter設定値またはRitsuの自己申告を実利用証跡として扱い、別条件の
  結果をLuna/highとして評価する。
- 緩和策: Gate Sでplatform管理のagent type、model ID、effort、fresh性を確認する。
- ゲート: 証跡不足は`inconclusive / blocked`とし、別modelやeffortへfallbackしない。

### P1: 主評価baselineと評価契約が未承認

- 失敗パターン: 専門担当自身の制作、Sol/high worker、異なるpromptやdispatch経路を同じ
  baselineとして混ぜ、速度・品質差をRitsuへ誤帰属する。
- 緩和策: 主評価を「専門担当自身の制作」と「Ritsu委譲」のend-to-end比較へ限定し、
  固定タスク、oracle、反復数、順序、欠測処理、閾値を結果取得前に承認する。
- ゲート: 未固定条件がある間はGate Mを実行しない。

## 4. 解消済みの主要指摘

次の指摘は、改訂または人間判断によって解消した。

- Stage 4以前の古い前提と、一度に二人を迎える順序競合
- Kai、Toki、Genの正本責務を越える委譲例
- Gen中継時間を除外したworker単体速度だけの評価
- docs-onlyとコード試用を同じ加入根拠として扱う状態境界
- 同一成果物への交差writeと、依頼・結果・レビューの所有者混在
- 再作業不能を能力不足と混同する分類
- Stage 5先行を固定事実と未判断候補の両方として扱う記述

## 5. 継続監視する運用リスク

次の観点は現在の停止条件ではないが、試用結果で再確認する。

- Gen集中dispatchがqueueとrelayを増やし、新しいボトルネックにならないか
- 専門担当の契約詳細化とレビュー負荷が、Ritsuの速度差を相殺しないか
- 1回の機能pilotを速度改善、品質非劣性、正式加入の根拠へ拡大解釈しないか
- Markdown成果物の結果をコード実装、TDD、自動化、回帰品質へ外挿しないか

blindレビュー、write境界を確認する。試用後は、実ログ、契約逸脱、重大指摘、再作業、
Gen負荷、残留リスクをレビューする。人間が最終合否とリスク受容を判断する。
