## 選択肢（導入手段。採否しない）

| 案 | 何か | 向く条件 | 向かない条件 |
| --- | --- | --- | --- |
| A 文書化コピー | 一覧と手順で複製。新実行物なし | まず手段を固定せず配りたい | 反復と衝突を機械で止めたい |
| B 取得適用スクリプト | git URL/パスから適用器が書く | 同じ取得元で繰り返したい | 新実行物を増やしたくない |

| D 参照ピン留め | ポインタだけ置く | 本文をコピーしたくない | 「置いて使える」を成功にしたい |
| E テンプレート新規 | 新規リポジトリを生成 | 空の新規だけが対象 | 既存リポジトリへ入れたい |

詳細は `docs/work/repo-install/kai.md`。

## 人間が決めた配布モデル

- チームは、このリポジトリで育てる。
- 他リポジトリは、このリポジトリからインストールする。
- 更新も、このリポジトリから取得する。
- フィードバックは、このリポジトリへの PR とする。

残る比較は、入れ方だけに寄せる。案 D（参照だけ）と案 E（新規生成だけ）
は、更新取得と既存リポジトリへの導入を同時に満たしにくい。
案 A は更新手段が手順の再実行だけになる。残る有力は案 B と案 C。

## 推奨案

入れ方が決まるまで、実装 PLAN は出さない。比較の出発点は次である。

1. 書込み主体は導入先の人間。このリポジトリのエージェントは書かない。
2. 配布物は宣言した集合だけ。このリポジトリ全体（Mission Room を含む）
   は配らない。
3. 下流のインストール済みファイルは、上流のピンである。独自正本にしない。
4. 入れ方はインストーラ（人間指定 A、Kai 案B）。git 従属は採らない。

## 推奨理由

- REQ-05 を維持したまま、導入先へファイルを置くには、実行主体を
  導入先の人間に置く必要がある。
- FACT-02 を必須集合にすると、導入先の `AGENTS.md` と起動口を
  実験場人格で置き換えうる（Rin P0-2, P1-8）。
- 案Bの適用器は高権限の書込み口になる（Rin P1-4）。採否前に置かない。

## Pros / Cons（依頼を続ける場合）

| | 続ける | やらない / 縮小する |

| Cons | 一括配備になりうる。上書きと効力の判断が要る | 「インストールできる」は満たさない |
