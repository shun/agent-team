## 実装単位の候補

実装単位は、将来の作業契約に載せうる塊である。採否でも
推奨でもない。各単位は、未固定事項が残るあいだ開始不能と
する。

### U-SRC このリポジトリ内の新規インストーラ成果物

対象は、導入手段を実行するための新規ファイルを、この
リポジトリ内へ置くことである。FACT-01 の記載では、ルートに
README、install スクリプト、`package.json` は無い。新規設置
なら、既存ファイル更新より隔離条件は狭い。

開始できない理由:

- 置くパス、言語、実行形態が未固定（Q-D-03、Q-B-02）
- 成果物が読む配布集合が未固定（Q-B-01、Q-I-01）
- 実行主体が未固定（Q-I-02）
- 新規ファイルでも、間接 write（lockfile、生成物、
  `node_modules` 等）の集合が未固定
- 正本・adapter を「配布できる形に直す」更新は、REQ-06 の
  対象になり、人間承認なしでは開始できない

既存の `scripts/run-plan.ts` を触る場合、この単位は新規
設置ではなく既存ファイル更新になる。その採否はしない。
触るなら、後述の隔離条件が追加で必要になる。

## 隔離

隔離は、誰のどの作業コピーへ書くかを、開始前に技術的に
分けることである。repository manifest や instruction 上の
allowlist 遵守は、隔離の証拠にしない。

### 今回の計画レビュー

今回の直接 write は
`docs/work/repo-install/ritsu.md` の新規作成だけである。
正本、adapter、既存コード、`tmp/PLAN.md` は変更しない。
リポジトリ外への書き込み、ネットワーク、VCS は行わない。

### 将来、このリポジトリ内へ実装する場合

新規ファイルだけを write 集合にする場合でも、次を契約に
固定する必要がある。

- 直接 write のパス一覧
- 間接 write の有無（生成物、キャッシュ、lockfile）
- 基準版 hash
- 正本・adapter（REQ-06 の列挙）を write 集合に含めないこと
- write 前に、許可外パスへの差分が出たら停止すること

既存ファイルを更新する場合は、上記に加えて次が無いと
委譲できない。

- 使い捨て作業コピー、または同等の技術的 write 隔離
- 対象所有者
- write 前競合停止
- 独立差分確認の主体
- 復旧主体

技術的 write 隔離を用意できない環境では、既存ファイル
更新を Ritsu へ委譲しない。

### 将来、導入先リポジトリへ書く場合

導入先への配置を、このリポジトリのエージェント作業として
行う契約は、REQ-05 と両立しない。その契約は開始できない。

導入先への配置を、導入先の人間操作とする場合、Ritsu の
write 集合はこのリポジトリ内に閉じる。導入先の既存ファイル
更新は、Ritsu へ委譲しない。導入先で別作業 ID を切るなら、
その作業コピー、所有者、基準版、競合停止、独立差分、復旧
主体を、その契約で改めて固定する。

対象が第三者または本番を含むかは未確認（Q-B-03）である。
含む場合の許容は決めない。含む前提のまま write 集合を
書くことはできない。

### 将来の実装契約で必要な証跡の性質

実装を開始する契約には、少なくとも次の性質の記録欄が

  性能や安全強制の証明に使わない

- 実行したコマンドと、秘密情報・生ログを含まない結果要約

## 複合作業の成立条件

複合作業とは、複数ファイル、複数工程、通常のデバッグを
含む実行である。Ritsu は、依頼元の判断中核と受入れ確認を
代行しない。

開始前に、作業契約へ次を固定する。欠けたら開始しない。

| 欄 | 現在 | 欠けると起きること |
| --- | --- | --- |
| 目的 | 計画作成までは固定。製品の導入目的は未固定 | 完了の観測対象が書けない |
| 上流の人間判断 | REQ-02, REQ-03, REQ-04〜10 以外は未判断 | 配布集合と書込み主体が書けない |
| 入力 allowlist | 本レビューは固定。実装契約は未作成 | 未信頼入力と正本の区別ができない |
| 出力先 | 実装契約は未作成 | 依頼・結果・レビューが混線する |
| read/write allowlist | 実装契約は未作成 | 許可外 write を停止できない |
| 直接・間接 write 集合 | 未固定 | 隔離条件を判定できない |
| 基準版 | 未固定 | 競合停止と復旧ができない |
| 許可する裁量 | 未固定 | 手段の具体化が推測になる |
| 完了条件 | 未固定（Q-B-05） | 完了申告ができない |
| 検証条件 | 未固定。オラクルなし | 検証を実行できない |
| 停止・差戻し条件 | 本レビューは request.md にある。実装用は未作成 | 衝突時の扱いが推測になる |
| 再作業上限 | 本レビューは 1 回。実装用は未作成 | 再作業の打ち切りができない |
| 技術的 write 隔離 | 導入先または既存ファイルを含むなら未用意 | 既存ファイル更新を委譲できない |
| 対象所有者・復旧主体 | 未固定 | 事故時に戻せない |

成立しない条件:

- 要件分類、設計案と成立条件、QA オラクル、P0 / P1 / P2、
  Aira の統合判断を、Ritsu が埋める必要がある
- 指定の名前付き `ritsu`、または platform 別の指定 model
  条件が利用不能で、別条件へ fallback する必要がある
- 人間承認に結び付かない正本変更、VCS、merge、deploy、
  本番・高権限操作、外部送信が必要になる
- 許可外のリファクタリング、追加機能、ツール導入、
  read/write 範囲拡大が必要になる

U-SRC から U-VERIFY までを一つの作業 ID に載せることは、
複合作業になる。その塊は、上表が埋まるまで成立しない。
一部だけを短い作業に切る判断は、Hayate の境界検証および
人間判断へ戻す。Ritsu はスライスを採用しない。

外部再作業は 1 回までである。契約不足が残る再作業は、
実装に入らず上流へ戻す。
