## 共通前提と責務境界

今回の作業は計画である。PLAN 承認前の実装、VCS、deploy は行わない
（REQ-02, REQ-03）。人間が最終判断者である（REQ-04）。このリポジトリの
エージェント作業としては、リポジトリ外への書き込み禁止、正本と
adapter の無断変更禁止、許可外 VCS 禁止が確定している
（REQ-05 から REQ-09）。

どの案でも、次の責務は混ぜない。

- 配布物の採否と実験場ルールの転用は、人間判断である。
- 対象リポジトリへの書込み主体は、Q-I-02 の軸であり、ここでは決めない。
- 導入手段の設計は本文書、検証項目は Toki、リスク重大度は Rin、
  実装単位は後続、統合と最終提案は Aira、採否は人間である。

```text
このリポジトリ（取得元）
  -> 取得（clone / URL / テンプレート / 参照）
    -> 配布集合の選択（Q-B-01, Q-I-01, Q-I-03）
      -> 対象リポジトリへの配置（Q-I-02 の主体）
        -> 人間が観測できる配置結果
```

この流れは責務の境界であり、技術的強制を意味しない。instruction の
遵守を、書込み禁止や上書き防止の証明として扱わない。

### 強制、検知、検証の区別

全案に共通する。

- 技術的強制: 許可しない書込み、上書き、範囲外配布を、実行前に止められる
  能力。現時点の入力では、どの案もこの能力を持つと断定しない。
- 逸脱検知: 許可しない配置や、宣言と異なるファイル集合が起きたあと、
  差分として識別できる能力。検知は防止ではない。
- 事後検証: 取得元、配布集合、配置先、実行主体、結果の対応を、人間が
  追跡できること。検証手順と合否は書かない。

必要な証跡の性質は、取得元の識別（リポジトリと参照）、配布集合の宣言、
配置先パス、実行主体の識別、衝突時の分岐記録である。取得方法は問わない。

聞きたいことは、このリポジトリ固有の実験場ルールを他リポジトリへ

設計軸としての扱い:

- コピーする: 配布集合に正本・安全境界を含めうる。拘束するかは別判断。
- 参考としてコピーする: 配置はするが、導入先での効力は宣言に留まる。
- コピーしない: 正本本文を対象へ置かない。参照または局所 adapter のみ。

どの案も、配布集合をこの軸の値で差し替えられる形にする。特定の値を
採用済みとしては扱わない。

### Q-I-02 対象リポジトリへの書込み主体

聞きたいことは、インストーラ相当の書込みを、導入先の人間操作とするか、
このリポジトリのエージェント作業とするか、今は決めずエージェントが
導入先へ書かないことだけ固定するか、である。関連は REQ-05, REQ-15,
REQ-18, REQ-28。

設計軸としての扱い:

- 導入先の人間操作: 実行主体は対象側の人間。このリポジトリの
  エージェントは書かない。
- このリポジトリのエージェント作業: 確定正本のリポジトリ外書き込み
  禁止（REQ-05）と衝突しうる。成立には人間による安全境界の明示変更が
  先に必要であり、本作業では行わない。
- エージェント非書込みだけ固定: 手段は人間操作に寄せて比較する。
  将来の主体追加は別判断とする。

どの案も、実行主体を差し替え可能なスロットとして残す。主体を一つに
固定して採否しない。

## 案A: 文書化コピーセット

リポジトリの作業ツリーまたはアーカイブを複製元にすることである。

### 概要

取得と配置を、手順書とファイル一覧でつなぐ。

1. 取得元はこの git リポジトリである。clone、archive、作業コピーの
   いずれでもよい。手段の単一化はしない。
2. 配布集合は一覧として宣言する。FACT-02 の列挙を必須集合にはしない。

4. 更新は再複製である。同一手段で更新するかは Q-B-06 の軸として残す。

Mission Room と `scripts/run-plan.ts` は、入力上の配布候補ではない。
対象へコピーする前提にしない。

### 強制、検知、検証

- 強制: なし。手順書は技術的強制ではない。
- 検知: 宣言一覧と対象ツリーのパス集合を後から照合できる。
- 検証: 取得元、一覧の版、配置先、実行主体が記録されていれば、

### 運用、環境、保守

運用負荷は、複製手順の実施と一覧保守である。環境依存は、対象へ
ファイルを書けることと、このリポジトリを読めることに限る。
回避可能性は高い。手順を飛ばす、一覧と異なる集合を置く、既存ファイルを
上書きする、はいずれも止められない。保守は一覧と正本の同期である。
移行は、後からスクリプトや git 従属へ移す余地がある。後戻りは、
置いたファイルの扱い次第であり、削除は本作業の対象外である。

## 案B: 取得適用スクリプト

このリポジトリに置く適用手段が、この git リポジトリを取得元として
対象ディレクトリへファイルを適用する案である。実行主体は Q-I-02 の
スロットであり、ここでは人間にもエージェントにも固定しない。
直接の意味は、git URL または局所クローンを取得元にし、レジストリを
経由しないことである。

### 概要

取得と適用を、宣言された入力と適用器でつなぐ。

1. 適用器の置き場は、このリポジトリ内の後続実装対象である。置き場の
   確定は REQ-33 / Q-D-03 の軸であり、ここでは決めない。
2. 入力は、取得元（このリポジトリの URL またはパス）、参照
   （branch / tag / commit の識別）、配布集合、対象ディレクトリである。
3. 適用器は、宣言集合だけを対象へ書く設計とする。衝突時の既定は
   「書かない」を本案の性質として置く。上書きやマージへ変えるかは
   Q-B-04 の軸として残す。
4. 更新は、同じ適用器に新しい参照を渡すことである。含めるかは
   Q-B-06 の軸として残す。

適用器の存在は、このリポジトリのエージェントが導入先へ書くことを
意味しない。実行主体は Q-I-02 が決める。

### 強制、検知、検証

- 強制: 適用器が、宣言外パスへの書込みと、既定では衝突ファイルへの
  上書きを拒否できる余地がある。適用器を使わない複製は強制できない。
- 検知: 適用前後のパス集合、参照識別、拒否した衝突を記録できる。
- 検証: 取得元、参照、配布集合、対象、実行主体、適用結果の対応が
  残れば、人間が追える。合否は書かない。

### 運用、環境、保守

運用負荷は、適用器の保守と、実行時引数の固定である。環境依存は、
適用器が動く実行環境、git または同等の取得手段、対象への書込み権限
である。未確認の環境機能は利用可能と断定しない。回避可能性は、
適用器を使わず手コピーすること、引数を変えて範囲を広げることに残る。
保守は、配布集合と適用器の同期、参照の更新である。移行は、案Aの
一覧を入力にできる。後戻りは、適用器が削除をしないなら、置いた
ファイルの撤去は別手段である。

### 利点、制約、成立条件

| 観点 | 内容 |
| --- | --- |
| Pros | 反復適用と参照固定を、同じ取得元で繰り返せる。衝突時に「書かない」を手段の性質にできる。 |
| Cons | 新しい実行物とその実行環境が要る。適用器自体が高権限の書込み口になる。適用器を迂回する配置は止められない。 |
| 成立条件 | 後続で適用器の作成が人間に承認される。取得元をこの git リポジトリに限定できる。実行主体と対象ディレクトリが明示される。Q-I-02 がエージェント書込みを選ぶなら、その前に REQ-05 の扱いを人間が明示する。 |
| 成立しない条件 | 新しい実行物を置けない。対象環境で適用器も git 取得も使えない。「直接」がテンプレート新規作成だけ、または参照のみを指す場合。 |
| 限界 | 適用成功は、チームとして使える状態を保証しない。ネットワーク取得の可否、認証、プライベートリポジトリの扱いは未確認である。 |
| 要件ID追跡 | 満たしうる: REQ-01, REQ-02, REQ-17, REQ-21。作業制約: REQ-03 から REQ-09, REQ-15。仮説依存: REQ-16, REQ-18, REQ-20。未確定のまま残る: REQ-23, REQ-24, REQ-28, REQ-33。 |

### Why / Why not

Why: 「リポジトリから直接」を、git URL を取得元にした反復適用として
比較できる。Why not: 実行物を増やさず、git の従属関係だけで版を
固定したい場合は、案Cの方が配置モデルとして区別できる。

### Q-I 軸での見え方

- Q-I-01 コピーする: 適用集合に正本を含めうる。
- Q-I-01 コピーしない: 適用集合をポインタに縮小する。適用器は残る。

## 案C: Git従属配置

対象リポジトリが、このリポジトリを git の従属ツリーとして記録する案
である。正本本文は vendor 相当のパスに置き、対象ルートの adapter は
置かない、薄いポインタにする、従属ツリーから投影する、のいずれかを
Q-I-01 と Q-B-01 で選ぶ。直接の意味は、このリポジトリの git URL を
対象のバージョン管理履歴へ残すことである。

従属の具体形（submodule、subtree、同等の vendor ref）は実装選択であり、
ここでは「git オブジェクト識別で取得元を固定する」ことだけを共有する。

### 概要

配置の正本を、コピー結果ではなく git 参照にする。

1. 対象リポジトリは git リポジトリである。
2. このリポジトリを、固定した commit 識別で従属させる。
3. ツールがルート相対パスを要求する場合、投影または局所 adapter が
   追加で必要になる。必要かどうかは未確認であり、あることを前提に
   しない。
4. 更新は、従属参照の進め戻しである。対象側の VCS 操作になる。
   このリポジトリのエージェントは、許可外 VCS を行わない（REQ-07）。

### 強制、検知、検証

- 強制: 従属参照は、取得元と版を git で固定できる。ルートへの無断
  複製や、従属を使わない手コピーは強制できない。
- 検知: 従属参照の識別と、宣言された投影パスの有無を後から見られる。
- 検証: 対象履歴上の参照、取得元 URL、commit 識別、投影の有無が
  残れば、人間が追える。合否は書かない。

### 運用、環境、保守

運用負荷は、従属参照の追加と更新、必要なら投影の再実施である。
環境依存は、対象が git であること、従属を扱えることである。
ホスティング固有機能には依存しない。回避可能性は、従属を置かず
手コピーすること、参照を動かさずルートだけ編集することに残る。
保守は、このリポジトリ側の変更を、対象の参照更新へどう伝播するか
である。移行は、従属を外して案Aまたは案Bの複製へ移す余地がある。
後戻りは、参照削除と投影ファイルの扱いが分かれ、削除は対象外である。

### 利点、制約、成立条件

| 観点 | 内容 |
| --- | --- |
| Pros | 取得元と版を git 識別で残せる。正本本文を対象ルートへ置かない選択と両立しやすい。ホスト非依存で「直接」を表せる。 |
| Cons | 対象が git であることが前提になる。ルート相対パスを要求するツールとは、投影なしでは噛み合わない可能性がある。対象側に VCS 操作が必要になる。 |
| 成立条件 | 対象が git リポジトリである。人間が「インストール」を git 従属として観測してよい。Q-I-02 の書込みが、従属追加とその投影に対応する。ツールが vendor パスを読むか、投影を別途認める。 |
| 成立しない条件 | 対象が git ではない。インストール成功が、従来パスへの実ファイル配置だけを指し、従属も投影も認めない。第三者または本番が git 従属を拒否する（Q-B-03）。 |
| 限界 | 従属の存在は、チームとして使える状態を保証しない。sparse な部分取得は未確認である。対象側 VCS を誰が行うかは Q-I-01 の転用可否にも依存する。 |
| 要件ID追跡 | 満たしうる: REQ-02, REQ-17, REQ-21。作業制約: REQ-03, REQ-05, REQ-07。仮説依存: REQ-16, REQ-22。未確定のまま残る: REQ-23, REQ-25, REQ-27, REQ-32。 |

### Why / Why not

Why: 複製スナップショットではなく、取得元のオブジェクト識別を対象へ
残す配置として、案A/Bと区別できる。Why not: 空でない既存リポジトリや
非 git 対象を広く含むなら、成立条件が先に狭まる。

### Q-I 軸での見え方

- Q-I-01 コピーする: 従属に加え、ルートへ本文または adapter を投影する。
- Q-I-01 コピーしない: 従属またはポインタだけを残し、本文は投影しない。
- Q-I-02 人間操作: 対象側の人間が従属を追加する。
- Q-I-02 エージェント作業: 対象への VCS をこのリポジトリの
  エージェントが行うことになり、REQ-05 と REQ-07 に触れる。
- Q-I-03 一括を避ける: 従属は残し、投影集合を最小にする。

## 案D: 参照ピン留め

対象リポジトリへ、このリポジトリの URL と参照識別を持つ短いポインタ
だけを置き、正本本文や adapter 一式は複製しない案である。直接の意味は、
実行時または運用上の参照先をこのリポジトリに固定し、配布物の複製を
主手段にしないことである。

### 概要

配置量を最小にし、正本の所在をポインタで示す。

1. 対象へ置くのは、取得元 URL、参照識別、任意の内容ハッシュ、
   必要なら「正本はここを見ること」という局所記述である。
2. FACT-02 の本文や adapter 一式は、対象へ置かない。置く場合は
   別案へ寄せる。
3. ツールが局所 adapter を要求するかは未確認である。要求する場合、
   本案は成立しない条件側へ寄る。推測で adapter を足さない。
4. 更新は、ポインタの参照識別を書き換えることである。

### 強制、検知、検証

- 強制: なし。ポインタは、ツールや人間が読むことを強制しない。
- 検知: ポインタの有無、参照識別、対象に正本本文が混入していない
  ことは、後から照合できる。
- 検証: ポインタ内容、参照先の識別、配置した主体が残れば、人間が
  追える。参照先を実際に取得できたかは、検証手順を決めない。

### 運用、環境、保守

運用負荷は、ポインタの作成と参照更新である。環境依存は、必要なときに
参照先を読めることである。オフラインや取得不能を、利用可能とは
断定しない。回避可能性は高い。ポインタを無視する、参照を動かさず
局所に正本を持ち込む、は止められない。保守は、このリポジトリ側の
移動や改名に対するポインタ更新である。移行は、後から案A/B/Cで実体を
置く余地がある。後戻りは、ポインタファイルの扱いであり、削除は
対象外である。

### 利点、制約、成立条件

| 観点 | 内容 |
| --- | --- |
| Pros | 対象への書込み面が小さい。既存ファイルとの衝突が起きにくい。正本の単一所在を保ちやすい。 |
| Cons | 局所に定義が無いため、ツールがリモート正本を読めないと使えない。拘束力は宣言に留まる。REQ-16 の「配置して使える」とは食い違いうる。 |
| 成立条件 | インストール成功を、局所複製ではなく参照の固定として観測してよい。Q-I-01 がコピー不要、またはポインタのみを許す。参照先を、必要な主体が読める。 |
| 成立しない条件 | インストール成功が FACT-02 相当の局所配置を指す。ツールが局所 adapter なしでは動かない。対象が完全オフラインで、参照先のキャッシュも無い。 |
| 限界 | ポインタは技術的強制ではない。導入先での原則維持（REQ-22）は、効力の判断（Q-I-01）なしには置けない。 |
| 要件ID追跡 | 満たしうる: REQ-02, REQ-17。作業制約: REQ-03, REQ-05, REQ-06。仮説と食い違いうる: REQ-16, REQ-19。未確定のまま残る: REQ-23, REQ-24, REQ-27, REQ-30。 |

### Why / Why not

Why: 複製しない導入として、一括配置を主手段にする案と区別できる。
Why not: 「インストール」が局所配置を指すなら、本案は導入手段ではなく
案内手段になり、REQ-01 の比較対象から外れる。

### Q-I 軸での見え方

- Q-I-01 コピーする: 本案の主旨と食い違う。コピーするなら案A/B/Cへ寄せる。
- Q-I-01 コピーしない: 本案がそのまま残る。
- Q-I-02 人間操作: ポインタを置くのは導入先の人間。
- Q-I-02 エージェント作業: 対象への書込みがエージェントなら REQ-05 に触れる。
- Q-I-03 一括を避ける: 本案は一括配置をしない。優先の採用ではない。

## 案E: テンプレート新規作成

このリポジトリから作ったテンプレートで、新しいリポジトリを生成する案
である。既存リポジトリへの後付けは、本案の主経路にしない。直接の意味は、
テンプレートの生成元をこのリポジトリにすることである。ホスト固有の
テンプレート機能に限定するかは Q-B-03 の軸として残す。

### 概要

導入を、既存ツリーへの書込みではなく、初期ツリーの生成にする。

1. このリポジトリ、またはそこから作ったテンプレート枝を生成元にする。
2. 新しいリポジトリの初期ファイルは、Q-I-01 と Q-I-03 で選んだ配布
   集合である。
3. 既存リポジトリ、エージェント設定済みリポジトリは、本案では対象外
   とし、他案へ送る。
4. 更新は、生成済みリポジトリへの再適用であり、本案の主経路ではない。
   Q-B-06 が更新を含むなら、案A/B/Cとの併用が必要になる。

### 強制、検知、検証

- 強制: 生成後の改変は止められない。生成時の集合は、テンプレート内容
  で固定できる余地がある。
- 検知: 生成元参照と、初期ツリーのパス集合を後から照合できる。
- 検証: 生成元、テンプレート版、新規リポジトリの所在、生成主体が
  残れば、人間が追える。合否は書かない。

### 運用、環境、保守

運用負荷は、テンプレートの同期と、新規作成時の生成である。環境依存は、
テンプレート機能または同等の生成手段である。GitHub テンプレートに
限ると、REQ-21 の仮説（特定ホストに限定しない）と食い違う。
回避可能性は、テンプレートを使わず手で新規作成することに残る。
保守は、このリポジトリとテンプレートの乖離である。移行は、生成後の
リポジトリを案B/Cで更新する余地がある。後戻りは、新規リポジトリ
そのものの扱いであり、本作業の対象外である。

### 利点、制約、成立条件

| 観点 | 内容 |
| --- | --- |
| Pros | 空の新規リポジトリでは衝突が起きにくい。初期集合を生成元側で揃えられる。 |
| Cons | 「いろいろなリポジトリ」のうち既存分を覆わない。テンプレートと正本の乖離が残る。ホスト固有にすると可搬性が下がる。 |
| 成立条件 | 対象の主クラスが新規または空である。生成元をこのリポジトリに辿れる。Q-I-02 の書込みが、新規リポジトリの生成として観測できる。 |
| 成立しない条件 | 既存リポジトリへの導入が必須である（REQ-01, Q-B-03）。特定ホストのテンプレート以外を認めない、かつ対象がホスト外である。更新・再導入を同一手段で扱うことが必須である（Q-B-06）。 |
| 限界 | 生成は、導入先での原則維持を保証しない。既存衝突、上書き、アンインストールは設計範囲に入らない。 |
| 要件ID追跡 | 満たしうる: REQ-02, REQ-17。部分的: REQ-01（新規に限る）。作業制約: REQ-03, REQ-09。未確定のまま残る: REQ-21, REQ-25, REQ-26, REQ-32。 |

本案だけでは REQ-01 を覆えない。

- Q-I-01 コピーしない: 初期ツリーをポインタまたは最小 adapter にする。
